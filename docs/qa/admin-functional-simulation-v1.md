# freepasserp.com v1 — ADMIN 기능 시뮬레이션 / Work 구현 기준

작성일: 2026-09-13
상태: 구현 전 기능 검증 계약. 실제 테스트 실행 결과가 아님.
기준: `docs/MASTER-v1.md`, `AGENTS.md`, `docs/ui/atom-first-admin-ui.md`
목적: Work가 ADMIN을 구현할 때 화면 모양만 맞추지 않고, 상품 SSOT → 검색 → 상세 → 접수 → 접수목록 → 접수상세가 실제 업무처럼 이어지는지 검증하기 위한 시뮬레이션.

---

## 0. 최상위 완료 기준

ADMIN v1의 첫 수직 흐름은 아래 한 줄이 끊김 없이 돌아가야 한다.

`공급사 RAW → Adapter/Mapping → Canonical Product → Search/Filter → Product Detail → 선택 Offer → Application Draft → Application Snapshot → Application List → Application Detail → 계약서/필수서류/인도/취소`

핵심 원칙:
- 목록 = 찾기
- 상세 = 확인
- 업무패널 = 실행
- 화면은 원자를 다시 해석하지 않고 Canonical 값을 포맷한다.
- 검색에서 일치한 Offer는 상세와 접수까지 유지한다.
- 현재 상품이 바뀌어도 이미 저장한 접수 Snapshot은 바뀌지 않는다.
- 미확인값을 0/불가/무제한/특정 트림으로 추측하지 않는다.
- 기존 ERP/Firebase/API/시트에 fallback하지 않는다.

# A. 상품 검색 / 목록 시뮬레이션

## SIM-A01 — 모델명만 검색
**상황**: 관리자가 검색창에 `쏘나타` 입력.

**데이터**
- 상품 P1: 모델=쏘나타, 세부모델 미확인
- 상품 P2: 모델=쏘나타, 세부모델=DN8
- 상품 P3: 모델=쏘나타, 세부모델=디 엣지
- 상품 P4: 모델=K5

**기대**
1. P1/P2/P3는 검색 대상.
2. P4 제외.
3. P1은 `세부모델 미확인` 상태를 숨기지 않는다.
4. 목록 카드에 없는 트림을 만들어 붙이지 않는다.
5. 상품 수와 실제 보유 차량 대수의 의미를 혼용하지 않는다.

---

## SIM-A02 — 세부모델 정확 검색 + 부분 후보
**상황**: `쏘나타 DN8` 검색.

**기대**
- P2 = EXACT.
- P1 = 모델까지만 확인된 상품이므로, 정책상 부분 후보를 제공하는 관리자 화면에서는 PARTIAL로 별도 표시 가능.
- P3 = 다른 세부모델로 확인됐으므로 PARTIAL에도 포함하지 않음.
- EXACT 수와 PARTIAL 수를 합쳐 `조건 일치 상품 수`라고 표시하지 않음.

---

## SIM-A03 — 필터 OR / AND
**상황**: 모델 `쏘나타 OR K5`, 계약기간 `36개월`, 보증금 `0원`.

**기대**
- 같은 축 모델 선택은 OR.
- 모델축과 기간/보증금축은 AND.
- 모든 조건을 실제 하나의 Offer가 만족하는 상품만 정확 결과.

---

## SIM-A04 — 서로 다른 Offer를 섞으면 안 됨
**상품**
- Offer A: 18개월 / 월 700,000 / 보증금 3,000,000
- Offer B: 36개월 / 월 650,000 / 보증금 0

**검색**: `18개월 + 월 750,000 이하 + 보증금 0`

**기대**
- 검색 실패.
- A의 18개월/가격과 B의 보증금을 합쳐 허구의 18개월 무보증 상품을 만들지 않는다.
- 필터 옆 개수도 같은 Offer 관계를 유지한다.

---

## SIM-A05 — 기간 검색 시 카드 가격
**상황**: 같은 상품에 24/36/60개월 Offer가 있고 60개월이 가장 저렴함. 관리자는 24개월 필터 선택.

**기대**
- 카드 대표 가격 = 24개월 일치 Offer 가격.
- `전체 기간 중 최저가`를 크게 보여 사용자가 24개월 가격으로 오해하게 하지 않는다.
- 카드에서 선택된 offer_id를 상세로 전달한다.

---

## SIM-A06 — 공란과 0원 구별
**상황**: 공급사 원문 보증금이 공란.

**기대**
- 보증금=`미확인`.
- `0원`, `무보증`으로 검색되지 않음.
- 카드에 `보증금 0원` 표시 금지.
- ADMIN 상세에서는 필요 시 `보증금 미확인` 표시.

---

## SIM-A07 — 정책 검색
**상품 정책**
- P1: 카드결제 가능(대상=월대여료)
- P2: 카드결제 가능(대상=보증금만)
- P3: 카드결제 미기재

**검색**: `월 대여료 카드결제 가능`

**기대**
- P1 정확 일치.
- P2 제외.
- P3는 불가가 아니라 미확인. 정확 일치에는 포함하지 않음.

---

## SIM-A08 — 필터 항목 찾기
**상황**: 정책 필터가 많아지고 관리자가 상세필터 검색창에 `후불` 입력.

**기대**
- `결제시점 > 후불` 항목으로 이동/노출.
- 검색어 입력 자체로 필터가 자동 선택되지 않음.
- 사용자가 값을 선택한 뒤 적용해야 실제 상품검색 조건이 변경됨.

---

# B. 목록 → 상세 연속성 시뮬레이션

## SIM-B01 — 선택 Offer 유지
**상황**: 36개월 조건으로 검색된 상품 클릭.

**기대**
- 상세 진입 시 36개월 Offer가 선택된 상태.
- 월대여료/보증금/약정주행거리/Offer-scope Policy 모두 36개월 기준.
- 상세가 임의로 최저가 Offer나 첫 번째 Offer로 돌아가지 않음.

---

## SIM-B02 — 상품 선택 변경
**상황**: 목록에서 A → B → C 상품을 연속 클릭.

**기대**
- 가운데 상세만 즉시 해당 상품으로 전환.
- 오른쪽이 단순 접수목록 상태라면 목록 유지.
- 선택 상품 강조는 하나만 존재.
- 이전 상품의 Offer 선택이 새 상품의 Offer ID로 잘못 재사용되지 않음.

---

## SIM-B03 — 부분 매칭 상세
**상황**: 모델만 확정된 상품 상세.

**기대**
- 모델까지만 표시.
- 세부모델/트림 미확인 상태를 명확히 표현.
- 빈 트림을 인기 트림/기본형으로 대체하지 않음.
- 공급사 원문은 관리자 진단 접기 영역에서만 필요 시 확인.

---

# C. 상품 → 신규접수 시뮬레이션

## SIM-C01 — 상품 상세에서 접수하기
**상황**: 관리자 A상품 36개월 Offer 확인 후 `접수하기` 클릭.

**기대 UI**
- LEFT 상품목록 유지.
- CENTER A상품 상세 유지.
- RIGHT만 `신규접수`로 변경.

**기대 데이터**
- Draft에 product_id + product_version + offer_id 저장.
- Offer의 기간/대여료/보증금/약정주행거리/정책을 Draft 기준으로 유지.

---

## SIM-C02 — 접수 중 다른 상품을 구경
**상황**
1. A상품 36개월로 신규접수 열기.
2. 고객명 일부 입력.
3. 왼쪽에서 B상품 클릭해 상세를 구경.

**기대**
- CENTER는 B상품을 보여줄 수 있음.
- RIGHT Draft의 접수 대상은 여전히 A상품 36개월.
- 입력한 고객명 보존.
- A→B로 접수상품을 바꾸려면 명시적 `접수 상품 변경` 동작 필요.
- 단순 목록 탐색이 Draft를 조용히 바꾸면 실패.

---

## SIM-C03 — Draft에서 접수 상품 변경
**상황**: 사용자가 의도적으로 접수상품을 A→B로 변경.

**기대**
- 변경 전 A상품/Offer와 변경 후 B상품/Offer를 보여줌.
- 고객 입력값은 유지.
- 상품/Offer 의존 입력이 있다면 재검토 표시.
- 사용자가 확인해야 최종 Draft 변경.

---

## SIM-C04 — 현재 상품이 Draft 중 변경됨
**상황**
- Draft 시작 시 36개월 월 920,000원.
- 저장 직전 Canonical 최신 버전이 월 950,000원으로 변경.

**기대**
- 920,000원으로 조용히 최신 상품 접수 확정 금지.
- `조건 변경됨` 표시.
- 이전 Draft와 최신값 차이 보여줌.
- 사용자 확인 후 최신 조건으로 진행하거나 접수를 중단.
- 이미 저장된 과거 접수와는 다른 문제임.

---

## SIM-C05 — 필수입력 검증
초기 최소 접수 필수값은 현재 합의 기준으로 `차량 선택 / 영업채널 / 담당자 / 고객명`을 중심으로 검토한다. 연락처 등 실제 필수 여부가 MASTER와 최신 사용자 결정에서 확정되지 않았으면 UI 구현자가 임의로 필수화하지 말고 `DECISION REQUIRED`로 남긴다.

**기대**
- 필수값이 없으면 저장 차단.
- 어떤 값이 빠졌는지 해당 필드 근처에 표시.
- 입력값 전체 초기화 금지.

---

## SIM-C06 — 저장 버튼 더블클릭 / 재시도
**상황**: 네트워크 지연으로 사용자가 `접수 저장` 두 번 클릭 또는 클라이언트 재시도.

**기대**
- 접수 1건만 생성.
- 같은 제출 의도를 식별할 idempotency 기준 필요.
- 버튼 로딩 상태만으로 서버 중복방지를 대체하면 안 됨.
- 실제 저장 성공 후 새 접수번호를 반환.

---

## SIM-C07 — 저장 성공
**기대**
- Application Snapshot 생성.
- 접수목록에 새 건 표시.
- 새 건이 현재 필터 때문에 목록에 안 보이면 `접수 저장 완료 + 바로가기` 제공.
- 현재 상품 변경과 독립된 Snapshot.

---

# D. 접수목록 / 접수상세 시뮬레이션

## SIM-D01 — 목록 스캔
관리자가 스크롤만으로 알아야 할 것:
- 고객명
- 차량명
- 접수일/접수번호
- 계약서 완료 여부
- 필수서류 완료 여부
- 인도완료 여부
- 취소 여부

**기대**
- 공급사 원문/차대번호/배기량/내부 메타를 목록에 억지로 노출하지 않는다.
- 상세 확인이 필요한 정보는 접수상세로 이동.

---

## SIM-D02 — 더블클릭 접수상세
**기대**
- RIGHT만 `접수상세`로 전환.
- LEFT/CENTER 상품 탐색 문맥은 유지 가능.
- 상세 상단에 `접수 당시 조건`임을 명확히 표시.
- 현재 판매상품의 최신 가격과 혼동 금지.

---

## SIM-D03 — 계약서 체크
**상황**: 계약서 완료 체크.

**기대**
- contractCompleted=true.
- 처리시각/처리자 기록 가능한 이벤트 구조 필요.
- 대표 상태가 CONTRACTED로 파생될 수 있음.
- 필수서류 상태를 자동으로 완료시키지 않음.

---

## SIM-D04 — 필수서류 체크
**기대**
- documentsCompleted=true/false 독립 사실.
- 계약서와 서류의 강제 선후관계는 현재 별도 확정되지 않았으므로 Work가 임의로 하드코딩하지 않음.
- 필요 시 경고는 가능하나 차단 규칙은 `DECISION REQUIRED`.

---

## SIM-D05 — 인도완료
**기대**
- deliveryCompleted=true.
- 대표 상태 DELIVERED.
- 향후 정산 대상 생성의 근거가 될 수 있지만 정산 자동확정/자동지급은 금지.
- 실제 정산 모듈이 연결되기 전에는 `인도완료` 사실만 정확히 보존.

---

## SIM-D06 — 잘못 체크한 진행값 정정
**상황**: 인도완료를 실수로 눌렀다가 해제.

**기대**
- 값만 지우고 흔적 삭제 금지.
- 전/후 값, 변경자, 시각, 사유를 남길 이벤트/감사 구조 필요.
- 이미 후속 정산이 생성된 경우 영향 검토 필요.
- 정산 연동 전 단계에서는 적어도 정정 이벤트 설계를 막지 않도록 데이터 모델 구성.

---

## SIM-D07 — 취소
**기대**
- cancellationReason 필수.
- CANCELLED 상태.
- 기존 접수 Snapshot 삭제 금지.
- 계약/서류/인도 기존 사실을 물리 삭제하지 않음.
- 취소 후 일반 진행체크를 조용히 계속 변경할 수 없게 함.

---

## SIM-D08 — 상품 현재값 변경 후 과거 접수 열기
**상황**
- 현재 상품 월대여료 950,000원.
- 과거 접수 Snapshot 920,000원.

**기대**
- 접수상세 = 920,000원.
- `현재 상품 보기/비교`는 별도 행동.
- 현재값을 접수값에 자동 덮어쓰기 금지.

---

# E. 공급사 RAW → Canonical 시뮬레이션

## SIM-E01 — 같은 의미의 다양한 표현
**원문**
- `카드 가능`
- `카드결제 O`
- `신용카드 가능`

**전제**: 해당 출처/문맥에서 이 세 표현이 CARD_PAYMENT=true로 승인된 매핑.

**기대**
- 같은 Canonical Policy로 변환.
- 매 수집마다 AI 재판단 금지.
- 원문 표현은 근거로 보존.

---

## SIM-E02 — 비슷해 보여도 다른 정책
**원문**
- `카드 가능`
- `보증금만 카드 가능`
- `승인 시 카드 가능`
- `카드 불가`

**기대**
- 모두 같은 true로 뭉개지 않음.
- 가능여부 + 적용대상 + 조건을 분리.
- 미지원 의미면 REVIEW_REQUIRED.

---

## SIM-E03 — 모델까지만 제공
**원문**: `현대 쏘나타`

**기대**
- Canonical 모델=쏘나타.
- 제조사/원산지는 마스터 관계에서 검증/파생 가능.
- 세부모델/트림은 미확인.
- 정상 부분매칭 상품으로 저장 가능.

---

## SIM-E04 — 세부모델까지 제공
**원문**: `쏘나타 DN8`

**기대**
- 해당 세부모델 노드까지 확정.
- 트림 미확인.
- 같은 모델의 다른 세부모델 상품과 구분.

---

## SIM-E05 — 제조사/모델 충돌
**원문**: 제조사=`현대`, 모델=`K5`

**기대**
- 시스템이 몰래 `기아 K5`로 고친 후 정상처리하면 실패.
- `CONFLICTING_VEHICLE`.
- 원문 그대로 보존.
- 관리자 검수 후 Canonical 결정.

---

## SIM-E06 — 보증금 공란
**기대**
- UNKNOWN.
- 0원으로 생성 금지.
- 무보증 필터 정확 일치 금지.

---

## SIM-E07 — 가격 단위 확인
**원문 헤더**: `월료(만원)` / 값 `89`

**기대**
- 승인된 Source Contract에서 단위가 확인되면 890,000원.
- 단위 없는 `89`는 동일하게 처리하지 않음.

---

## SIM-E08 — 공통 정책만 변경
**상황**
- 상품행은 동일.
- 시트 상단 공통 안내가 `매월 후불` → `첫 달 선불, 이후 후불` 변경.

**기대**
- 상품행 해시만 보고 `변경 없음`으로 처리하지 않음.
- 영향받는 상품 Policy 재검증.
- 기존 접수 Snapshot 변경 금지.

---

## SIM-E09 — 일부 페이지/탭 수집 실패
**기대**
- 실패 범위를 기록.
- 빠진 상품 전체를 판매중지/삭제로 처리하지 않음.
- 마지막 확정값을 보존하되 최신성 경고 가능.

---

## SIM-E10 — 동일 원문 재수집 / 행 재정렬
**기대**
- 동일 상품/Offer 중복 생성 금지.
- 시트 행번호를 영구 상품 ID로 사용하지 않음.

---

## SIM-E11 — 매핑 규칙 수정
**상황**: 과거 승인 매핑이 잘못됐다고 확인.

**기대**
- 새 mapping version 생성.
- 영향받는 현재 상품 재처리 범위 미리보기.
- 과거 Application Snapshot 재해석 금지.
- 변경사유/변경자 기록.

---

# F. UI 원자 최소노출 시뮬레이션

## SIM-F01 — 상품목록 카드
목록에 기본적으로 필요한 원자:
- 이미지
- 모델 / 세부모델 / 세부트림(확정된 범위까지만)
- 필요한 경우 상품구분
- 검색에 일치한 Offer의 기간 / 월대여료 / 보증금 또는 핵심 조건
- 핵심 Policy 1~3개
- 판매/출고 상태

기본 목록에 넣지 않을 것:
- 원산지
- 배기량
- VIN
- 공급사 원문 전체
- 내부 source row/schema
- 정책 코드/내부 ID
- 사용자가 현재 판단에 쓰지 않는 제원 나열

---

## SIM-F02 — 상품상세
상세는 `차량정보 / 선택옵션·색상 / 제원 / Offer / Policy`를 구획한다.

원칙:
- 값이 있을 때만 보여주되, 업무상 중요한 미확인은 `미확인`으로 표시 가능.
- 원자를 새 문장으로 추론해 사실처럼 만들지 않음.
- 등록정보와 제조사 제원을 섞지 않음.
- 공급사 원문/검수메타는 ADMIN의 진단용 접기 영역.

---

## SIM-F03 — 관리자 접수목록
목록의 목적은 진행 모니터링. 상품의 모든 제원을 다시 보여주지 않는다.

`고객 + 차량 + 접수번호/일자 + 계약서/서류/인도/취소`가 우선.

# G. 장애 / 동시성 / 복구 시뮬레이션

## SIM-G01 — 저장 성공 응답 유실
**상황**: 서버에는 접수가 저장됐지만 클라이언트가 응답을 못 받아 재시도.

**기대**
- 동일 제출키로 기존 접수를 반환하거나 중복을 막음.
- 접수 2건 생성 금지.

---

## SIM-G02 — 두 관리자가 같은 접수 수정
**상황**: 관리자 A와 B가 동시에 접수상세 열기. A가 인도완료, B가 오래된 화면에서 서류상태 저장.

**기대**
- B의 저장이 A의 인도완료를 통째로 덮어쓰지 않음.
- 필드/이벤트 단위 변경 또는 optimistic concurrency 기준 필요.
- 충돌이 있다면 사용자에게 알림.

---

## SIM-G03 — 검색 후 상품 버전 변경
**상황**: 목록 검색시 product version 10, 상세 열기 전 version 11.

**기대**
- 상세가 최신을 보여주는 경우 목록 조건과 달라졌음을 감지.
- 접수 직전 최신성 재검사.
- 오래된 Offer ID가 사라졌다면 조용히 다른 Offer 선택 금지.

---

## SIM-G04 — 새로고침 / 재로그인
**기대**
- 저장된 접수와 상태는 다시 조회 가능.
- 브라우저 state만으로 업무 데이터 유지하면 실패.
- 아직 Firebase 연결 전 Mock 단계라면 `데모 데이터`라고 명확히 구분하고 완료 처리 금지.

# I. 구현 보고 형식

Work는 각 기능을 아래 5단계 중 어디까지 했는지 분리해서 보고한다.

1. `CODED` — 코드 작성
2. `STATIC CHECKED` — 타입/정적 검사
3. `TESTED` — 해당 시뮬레이션 자동/수동 테스트 통과
4. `PERSISTENCE VERIFIED` — 실제 저장 후 재조회 확인
5. `DEPLOYMENT VERIFIED` — 배포된 미리보기에서 실제 동작 확인

`CODED`만 된 것을 `완료`라고 표현하지 않는다.

예:
`SIM-C06: CODED / TESTED, Firebase 미연결이라 PERSISTENCE VERIFIED는 미실행.`

# J. 미확정 — Work가 임의 결정하지 않을 것

- 연락처가 접수 필수값인지 여부
- 계약서/필수서류/인도 사이의 하드 게이트 여부
- 인도완료 후 정산 대상 자동생성 시점
- 취소 후 정산/환불 처리
- 실제 차종마스터 v1 데이터 이관 범위
- Firebase 프로젝트 ID/리전/Auth
- 실제 공급사 Source Contract
- Policy별 외부 노출 범위

이 항목은 구현 편의를 위해 임의로 확정하지 말고 `DECISION REQUIRED`로 남긴다.

## 한 문장 기준

> ADMIN은 ‘상품을 많이 보여주는 화면’이 아니라, 공급사 원문에서 검증된 Canonical 상품을 정확히 찾고, 실제로 함께 적용 가능한 Offer를 확인한 뒤 그 조건 그대로 접수하고, 접수 당시 조건을 지키면서 계약서·서류·인도·취소를 계속 관리하는 업무 도구다.
