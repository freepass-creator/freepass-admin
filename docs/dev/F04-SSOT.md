# F04 정산원장 — 시트 전체를 SSOT 로

## 접수 누락 읽기 전용 대조

`npx tsx scripts/f04-ssot.mts --reconcile --id <F04 문서 ID>`로 접수 탭과 ERP5 Firestore `settlement_rows`를 대조한다. 회사 GWS 로그인과 기존 Firestore 읽기 계정을 사용한다. 시트·서버·로컬 사본에 데이터를 쓰지 않는다.

- 차량번호와 접수일이 같은 행만 같은 접수로 본다. 2026-10-01 Admin 전환 뒤 시트에만 있는 행은 시트 행 번호로 확인한다. 날짜·차량번호가 불명확한 행과 보관 탭 출처 중 접수에서 찾을 수 없는 행을 별도로 표시한다.
- 서버의 마지막 실제 접수일, 미래 날짜 행 수, `_f04.at`이 남은 마지막 연동 시각을 따로 본다. 마지막 접수일은 마지막 동기화 시각을 뜻하지 않는다.
- 미반영 신규 접수는 원본과 Admin 중복을 먼저 확인하고 기존 Admin 접수 경로로 처리한다. 이미 청구·지급된 건이나 옛 분납·완납 탭을 일괄 재적재하기 전에 관제탑이 원본과 처리 이력을 확인한다.

## F04 접수에서 서버 원장으로 반영

2026-10-31 결정에 따라 ERP6 접수·정산이 전환되기 전까지 직원이 입력하는 F04 접수 탭을 반영한다. 기존 `f04-ssot.mts`의 시트 읽기·Firestore 대조와 기존 운영 쓰기 승인 검증을 사용한다.

- `npx tsx scripts/f04-ssot.mts --id <F04 문서 ID> --plan <새 계획 JSON 경로>`는 행 번호·추가·갱신·보류 이유만 기록한다. 파일은 새 이름으로 만든다. 서버와 시트 쓰기는 발생하지 않는다. F04 아래 보관 탭과 원장 내부의 옛 통합 원장 이상 건은 대조 목록에만 남긴다.
- 계약번호를 포함한 차량번호·접수일로 일치 여부를 판정한다. 중복되거나 정정·Admin 중복이 의심되는 건은 보류한다. 미확정 신규는 원본 값을 옮기고 취소 표기도 보존한다. 기청구·지급된 신규는 원본에 명확히 있는 확정액만 옮기고 부가세 또는 합계가 불일치하면 확인 대상으로 남긴다. 금액 빈칸은 미확인, 숫자/통화 형식 오류는 보류다. 보증금 칸의 명시적인 ‘무보증’만 0으로 읽는다. 청구 발송 확인은 체크가 꺼져 있어도 기청구로 기록한다. 시트의 청구 최종발송일을 우선하고, 빈칸이면 발송 증빙에서 확정할 수 있는 날짜를 사용한다. 발송일을 확인할 수 없으면 보류한다. 인도 전 예정일은 비우고 신규 산정 조건은 공란으로 둔다.
- 서버 메모·고객·영업채널·상태·금액은 기존 값을 유지한다. 기청구·지급 기재 또는 확정 증적이 있는 서버 행은 접수 조건도 자동 갱신하지 않는다. 새 동기화가 기록한 자동관리 칸은 이후에도 직원이 수정하면 그 값을 보존한다. 출처가 없는 기존 값과 달라진 경우는 보류 목록에 남긴다. 기존 확정 건의 원천 취소는 환수 확인으로 남긴다. 원천에서 사라진 행은 확인 목록에만 남긴다.
- 관제탑이 특정 계획을 확인하면 기존 승인과 승인된 `F04_SHEET_ID`·운영 서비스 계정을 갖춘 담당 환경에서 `npx tsx scripts/f04-ssot.mts --apply-plan <승인한 계획 JSON 경로>`를 실행한다. 신청일·원장·변경 내용 지문이 다르거나 서버에 동시 변경이 있으면 중단한다. 200행 이하는 쓰기와 감사 기록을 한 트랜잭션에서 반영하고 다시 읽는다. 기본 실행과 정기 예약은 적용 모드를 호출하지 않는다.
- PC1·PC3와 관리자 GitHub에서 기존 F04 반영 예약을 찾지 못했다. 이후 담당 실행기에 기존 예약이 확인되면 그 예약의 읽기 작업을 재사용한다. 없으면 **PC1 평일 09:10~17:40 30분 간격**, 중복 실행 건너뜀으로 **계획 생성만** 하는 Windows 예약을 제안한다. 스케줄러 실행 계정으로 GWS·Firestore 읽기, 겹침 방지, 최신 계획 경로, 신규 차이 있을 때만 관제탑 알림을 사전 검증한다. 승인 작업에는 예약을 연결하지 않는다.

## 2026-10-02 최신 사용자 결정 — 아래 과거 네 탭 합산을 대체

## 2. ★「수수료표」가 내 물음의 답이었다

어제 저는 「요율 칸에 정액이 섞여 있다 — 한 칸에 뜻이 둘이다」라고 적었다.
**섞인 게 아니라 셈법이 일곱 가지였다.**

| 셈법 | 줄 | 무엇 | 기계가 내나 |
|---|---|---|---|
| `대여료×기간` | 80 | 요율 (0.0475 · 0.0375 · 0.0325 · 0.0225) | 예 |
| `정액` | 23 | 600,000 / 500,000 꼴 | 예 |
| `차량가액` | 19 | 신차 선출고 — 차량가액 × 3.5% / 3.0% | 예 |
| `범위` | 20 | 「최대 9%」 | ★**사람이 정한다** |
| `구독료+정액` | 5 | 「12개월구독료 100% + 30만」 | ★**사람이 정한다** |
| `조건분기` | 2 | | |
| `한달렌탈료` | 1 | | |

```
기계가 낼 수 있나 —  예 122 · ★사람이 정한다 28 · 빈칸 6
```

★**「사람이 정한다」가 28줄이다.** 이걸 기계가 계산하려 들면 틀린다.
SSOT 는 이 구분을 **그대로** 담아야 한다 — 「모르는 것」이 아니라 「사람 몫」이다.

그리고 대표가 「아 예시공급사E 신차인가보네」 하신 것이 여기서 확인된다 —
신차는 `차량가액` 기준이거나 `범위`(최대 9%)라 **요율표의 재렌트 요율과 아예 다른 축**이다.

## 3. SSOT 를 어떻게 세우나

```
f04/
 ├ feeTable   156   ★셈법 정본. 열쇠 = 공급사 + 갈래 + 형태 + 계약기간
 ├ rows       568   실적 한 벌 (접수 95 + 완납 378 + 분납 48 + 취소 47)
 │                  열쇠 = 차량번호 + 접수일 · 「어느 탭에서 왔나」를 상태로 남긴다
 ├ progress   432   사람 작업 흔적 (정산 진행) — rows 와 차량번호로 잇는다
 ├ vehicles   465   차량대장 — 차 이름의 정본
 └ goods      360   _상품 — 차량가액·기간별
```

### 지킬 것

1. **읽은 줄 = 실은 줄 + 보류한 줄.** 조용히 사라지는 줄 0
2. **자리로 읽지 않는다** — 열 이름으로 붙인다. 원본은 열 자리가 흔들린다
3. **빈칸을 0 으로 만들지 않는다**
4. ★**청구월은 `청구년` + `청구월` 두 칸에서 세운다.** ERP5 의 `"2026-09"` 는 파생값이다
5. ★**날짜로 변한 값을 되돌린다** — 시트가 「2026-08」을 `46235` 로 바꿔 놨다
6. **파생 탭은 안 담고 대조에만 쓴다**
7. **두 번 돌려도 같다**(멱등)
