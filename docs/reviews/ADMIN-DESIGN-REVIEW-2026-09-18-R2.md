## 0. 결론

이번 브랜치의 디자인은 이전 시안보다 **명확하게 좋아졌다.**

특히 다음은 그대로 유지하는 쪽이 맞다.

- Pretendard 실제 로딩 + 한글 최소 크기 상향
- 본문 회색 대비 개선
- 표 목록선 복구
- 순백 대신 따뜻한 중립 바탕
- 저채도 민트 계열 강조
- 버튼 높이/표현 위계 통일
- 검색 + 세부필터를 한 컨트롤로 묶음
- 상품은 카드 / 접수·원장은 표로 역할 분리
- 목록 7 : 상세 3
- 좌측 상·하 두 판 중 실제 보는 판을 크게 쓰고 다른 판은 접기
- 전자계약을 별도 원장으로 만들지 않고 접수 원장의 “보기”로 취급
- 전자계약 상세를 접수 상세의 계약서 영역에서 펼치는 방향

이제 큰 틀을 또 바꾸는 것보다 **아래 남은 정합성 문제를 닫는 것이 우선**이다.

# 1. 지금 좋아진 것

## D-OK-01. 글자 문제가 상당히 정리됨
이전 시안의 가장 큰 문제 중 하나였던 “회색이고 답답함”이 많이 개선됐다.

- Pretendard Variable 실제 로드
- 글자 크기 16종 → 6단
- 최소 11px
- `ink / ink-2 / ink-3` 모두 읽을 수 있는 대비로 상향
- 숫자 `tabular-nums`

**판정: 유지.**

## D-OK-02. 표가 다시 ERP답게 읽힘
목록선을 없애 산뜻하게 만드는 방향에서 되돌아와:
- 행 구분선
- 머리줄 진한 경계
- 숫자 우측 정렬
- 선택행은 면칠 대신 선
- 정렬 가능한 머리

로 정리된 것은 맞다.

**판정: 유지.**

## D-OK-03. 상품 카드 / 업무 표 분리는 좋음
상품은 “차를 고르는 일”이라 이미지와 가격을 같이 보는 카드가 맞고,
접수·실적·원장은 “열을 따라 훑는 일”이라 표가 맞다.

모든 화면을 카드 또는 표 하나로 통일하는 것보다 이 구분이 업무 목적에 맞다.

**판정: 유지.**

## D-OK-04. 찾는 칸이 훨씬 좋아짐
검색어 + 지우기 + 세부필터 + 조건 토큰의 관계가 명확해졌다.

`세부필터`를 별도 떠 있는 버튼이 아니라 같은 검색 컨트롤 안에 넣은 것도 시각적으로 안정됐다.

**판정: 유지.**

## D-OK-05. 전자계약 방향도 좋아짐
전자계약이 별도 “원장”을 소유하지 않고 접수 원장을 거른 보기로 동작하는 방향이 맞다.

또 접수 상세의 “계약서” 줄 안에서 전자계약 내용을 펼치는 구조는:
- 현재 접수 맥락을 잃지 않고
- 전자계약을 나중에 제거/교체하기 쉽고
- 같은 접수의 사실을 두 화면에 중복 저장하지 않게 한다.

**판정: 유지.**

# 2. 지금 반드시 닫아야 할 디자인 문제

## D-P0-01. Desktop과 Mobile의 IA가 아직 서로 다른 제품이다

### Desktop
현재 NAV:
- 상품찾기
- 계약접수
- 정산관리
- 전자계약

### Mobile
현재 bottom tab:
- 상품
- 접수
- 실적
- 설정

그리고 `설정` 안에:
- 정산관리
- 전자계약

이 들어 있다.

이 구조는 안 맞는다.

**정산관리와 전자계약은 설정이 아니라 업무다.**

### 권장
대표가 “메뉴 넷 유지”를 확정했으므로 모바일도 같은 네 축을 쓴다.

> **상품 / 접수 / 정산 / 계약**

설정은:
- 우측 상단 사용자 메뉴
- 또는 계약/정산과 분리된 더보기 메뉴

로 보낸다.

Desktop과 Mobile에서 업무 개념을 다르게 분류하지 않는다.

---

## D-P0-02. 최신 전자계약 IA와 예전 화면전환 코드가 같이 남아 있다

최신 원칙:
- 전자계약 상세는 새 화면이 아니다
- 접수 상세의 “계약서” 영역에서 펼친다

그런데 `admin-shell.app.js`에는 여전히:

- `전자계약 보기`
- `전자계약으로`
- `계약서 발송`
- `S.screen = 'esign'`

으로 별도 화면으로 이동시키는 예전 코드가 남아 있다.

이건 단순 코드 정리가 아니라 **UI 동선이 두 벌 존재하는 것**이다.

### 조치
접수 상세에서:
- 계약서 행을 펼침
- 필요한 행동을 같은 상세 하단 action bar에서 실행

으로 통일한다.

전자계약 메뉴는 “계약 관련 접수를 모아 보는 필터 뷰”일 뿐,
접수 한 건의 상세를 새 화면으로 데려가는 목적지로 사용하지 않는다.

---

## D-P0-03. 모바일에 전자계약 상세 경험이 아직 없다
Desktop은 `ecSection()`으로 계약서 영역을 상세 안에서 펼치는 구조가 생겼다.

하지만 모바일 `mAppDetail()`은 아직:
- 계약서
- 서류
- 잔금
- 인도

타임라인만 있고 전자계약 상세/확장 UI가 없다.

결과적으로 같은 접수가:
- PC에서는 계약 상태와 고객 진행을 자세히 보지만
- 폰에서는 그 맥락을 잃는다.

### 조치
모바일 접수상세의 “계약서” 행도 accordion/section 형태로 펼친다.

PC와 내용은 같고 배치만 모바일에 맞춘다.

---

## D-P1-01. 모바일 터치 규격이 자체 규칙과 충돌
문서는:
- 폰의 실행 버튼 44px
- AI Core touch 규격 44px

을 강조한다.

하지만 실제:
- `.mbar .mb-ic` = 38px
- `.mchips .sb` = desktop `--h-btn` 28px

이다.

WCAG 최소 바닥을 넘느냐와 별개로 **자기 규격과 실제 화면이 다르다.**

### 권장
모바일의 “누르는 것”은 최소 hit-area 44px 확보:
- 앱바 아이콘
- 필터 chip
- 탭
- 작은 액션

시각적 면은 28~38이어도, 투명 padding/pseudo area로 터치영역은 44를 확보할 수 있다.

---

## D-P1-02. 화면에 보이는 상태명이 잔금 단계를 아직 완전히 반영하지 않는다
최신 진행은:

> 계약서 → 필수서류 → 잔금 → 인도

인데 `appStatus()`는 계약서 + 서류 완료 후 바로 **“인도 대기”**로 읽을 수 있다.

또 상단 설명도:
> 계약서 · 필수서류 · 인도를 처리합니다.

로 잔금이 빠져 있다.

이것은 기능 이전에 **보이는 정보구조의 오류**다.

### 조치
표시상태도:
- 계약서 대기
- 서류 대기
- 잔금 대기
- 인도 대기
- 인도완료

로 일치시킨다.

---

## D-P1-03. UI-SPEC / POLISH-NOTES / 실제 CSS가 조금씩 어긋나기 시작했다
현재 확인되는 예:

- `UI-SPEC`: 강조색 설명에 슬레이트 블루 `#2f6289`
- 실제 `admin-shell.html`: 민트 `#0c7d73`
- `POLISH-NOTES`: 표 줄높이 36px이라고 적혀 있음
- 실제 토큰 / UI-SPEC: 34px
- `UI-SPEC`의 측정 예시는 footer가 아직 38인 것처럼 남은 부분이 있음
- `mountSplit()` 설명에 “목록 1 : 상세 2” 문구가 남아 있으나 실제 핵심 규격은 7 : 3

이 상태를 두면 다음 AI가 다시 디자인을 흔든다.

### 조치
**실제 `admin-shell.html` 토큰을 기준으로 UI-SPEC을 한 번 정리하고 POLISH-NOTES는 히스토리 문서로 둔다.**

“현재 규격” 문서는 하나만 둔다.

---

## D-P1-04. 상단 KPI와 각 판의 count/footer가 중복될 가능성
현재:
- 페이지 상단 KPI
- 판 제목의 건수
- 판 footer의 건수/합계

가 동시에 존재한다.

정산에서는 상단 KPI가 의미가 있지만 상품/접수에서는 같은 숫자를 세 번 보여줄 가능성이 있다.

### 권장
- **정산**: 상단 KPI 유지
- **상품/접수**: 꼭 필요한 cross-panel 요약만 상단에 둔다
- 현재 판의 건수는 판 제목
- 현재 목록의 합계/이슈는 footer

“한 숫자는 한 역할” 원칙으로 중복을 줄인다.

---

## D-P1-05. 카드형 상품목록은 기본으로 좋지만 표 전환은 보조로 둔다
상품 카드 선택은 맞다.

다만 카드/표 전환을 자주 쓰는 주기능처럼 강조하면 화면의 선택지가 늘어난다.

권장:
- 기본: 카드
- 대량 비교/정렬 필요 시 표
- view toggle은 제목줄의 조용한 보조도구

기본 사용자가 “카드냐 표냐”부터 고민하게 만들지 않는다.

# 3. 세부 polish

## D-P2-01. 민트는 지금 정도가 적절
`#0c7d73` 계열은 이전 회청색보다 산뜻하다.

다만:
- 선택
- 성공
- 완료

가 모두 녹색 계열로 붙어 보이지 않도록 역할은 유지한다.

현재처럼:
- key = teal
- success = green
- warning = amber
- bad = red

로 분리하는 것이 맞다.

## D-P2-02. 카드 그림자는 더 늘리지 않는다
현재 pane/card shadow 정도면 충분하다.

내부 ERP에서 그림자를 더 키우면 다시 B2C dashboard처럼 보인다.

## D-P2-03. 모서리도 지금 정도에서 멈춘다
`chip 3 / control 5 / pane 8`은 적당하다.

더 둥글게 만들 필요 없다.

## D-P2-04. 빈 상태는 다음 polish 대상으로 적절
현재 문서가 스스로 적어 둔 것처럼 Empty state는 아직 기능적인 문구 수준이다.

다만 일러스트를 크게 넣기보다:
- 무엇이 없는지
- 왜 없는지
- 다음 행동 하나

만 명확하게 만드는 방식이 내부 ERP에 맞다.

# 5. 최종 판정

현재 디자인은 **“다시 설계할 단계”가 아니라 “정합성 닫고 실제 앱에 옮길 단계”**다.

특히 desktop의:
- 색
- 밀도
- 폰트
- 표
- 카드
- 검색
- 상세 배치

는 큰 방향을 유지한다.

남은 핵심은 시각 장식이 아니라:

> **PC와 폰이 같은 업무 구조를 말하게 만들고, 전자계약 동선을 하나로 만들고, 규격 문서를 실제 코드와 정확히 맞추는 것**

이다.
