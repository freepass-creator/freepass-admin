# 목록·상세의 칸 — 「이게 없으면 무엇이 안 되나」

> 대표 2026-09-17
> 「지금 너의 역할은 구글 시트로 하던걸 erp화 하는거니까 항목이랑 이런것들을
>  니가 알아서 넣고 구현해봐라…. 상품목록도 너무 항목이 없고 접수목록도 없고
>  상세패널 어떻게 구현할건지」

`LEDGER-ITEMS.md` 가 정산원장에 쓴 규칙을 그대로 쓴다 —
**한 칸마다 「이게 없으면 무엇이 안 되나」 에 답이 있어야 한다.
답이 없으면 그 칸은 안 넣는다.**

칸 이름을 «지어내지» 않았다. 둘 중 하나에서 가져왔다.

| 어디서 | 무엇이 | 읽는 도구 |
|---|---|---|
| ERP5 Firestore `products` (91 필드) · `policy` (81 원자) | 상품 쪽 전부 | `scripts/erp5-snapshot.mts` |
| F04 정산원장 「접수」 탭 (54 열) | 접수 쪽 전부 | `scripts/f04-ssot.mts` |

## 1. 상품 목록 — 열 칸

여섯 칸(차량·공급사·기간·월대여료·확정도)이었다. 「고객이 이 차 있어요?」 에
답하려면 **목록에서** 알아야 하는 것이 훨씬 많다.

| 칸 | 없으면 무엇이 안 되나 | 원자 |
|---|---|---|
| 사진 | — (있으면 훑기가 빠르다. 없어도 일은 된다) | `photo` |
| 차량 | 무슨 차인지 모른다 | `vehicle.modelId` + `subModelId`/`trimId` |
| **차량번호** | **실물이 배정됐는지를 모른다.** 번호가 없으면 「팔 수 있는 상품」이 아니라 「조건표」다 | `registration.vehicleNumber` |
| **연식** | 중고 장기렌트에서 값을 가르는 첫 숫자다 | `specs.modelYear` |
| **주행** | 연식과 «짝» 이다. 2022년식 8만km 와 2022년식 2만km 는 다른 차다 | `specs.mileageKm` |
| 공급사 | 누구에게 물어보는지 모른다 | `supplierName` |
| **상태** | **지금 나갈 수 있는지를 모른다.** 이게 없으면 출고불가 차를 상담한다 | `status` (즉시출고·출고가능·협의·출고불가) |
| 기간 | 대여료가 어느 기간의 값인지 모른다 | `offers[].termMonths` |
| **보증금** | 고객이 «지금 얼마를 내야 하나» 를 못 답한다 | `offers[].deposit` |
| 월 대여료 | 상품의 값 자체다 | `offers[].monthlyRent` |

### 넣었다 «뺀» 것과 그 이유

- **연료** — 칸을 따로 안 준다. 차 이름 뒤에 덧말(`.sfx`)로 붙인다.
  「가솔린」이 한 열을 먹을 만큼 자주 거르는 조건이 아니다.
- **약정주행** — 상세의 「대여 조건」 표가 이미 Offer 별로 다 보여 준다. 두 번 안 쓴다.
- **확정도(트림/확인 필요)** — 실측 746 중 **512가 TRIM**이다. 나머지도
  SUB_MODEL 6 · MODEL 4 · **UNMATCHED 224**. 「확인 필요」를 234줄에 달면
  그건 정보가 아니라 무늬다. ⇒ **차종을 아예 못 붙인 것(UNMATCHED·MODEL)만**
  「차종」 딱지를 단다.
- **차 이름의 겹말** — 실측 746 중 **486(65%)**이 `sub` 가 `model` 로 시작한다.
  「싼타페」+「싼타페 MX5 프레스티지」= 「싼타페 싼타페 MX5 프레스티지」.
  목록에서는 앞말을 떼고 그린다(`subTrim()`). 상세는 원문 그대로 둔다.

## 2. 접수 목록 — 열한 칸

여덟 칸이었다. 시트의 「접수」 탭은 **쉰네 열**을 들고 있었다. 그중 —

| 칸 | 없으면 무엇이 안 되나 | 시트 열 |
|---|---|---|
| 접수일 | 열쇠의 반쪽이다 (「★열쇠는 «차량번호 + 접수일»」) | `receivedAt` |
| **할 일** | 이 화면을 여는 «이유» 다. 그래서 둘째 칸이다 | (파생 — `blocked()`) |
| 고객 | 누구 건인지 모른다 | `customer` |
| 차량번호 | 열쇠의 나머지 반쪽 | `plate` |
| 차량 | 무슨 차인지 모른다 | `model` |
| **공급사** | **누구에게 청구하나.** 없으면 정산으로 못 넘어간다 | `supplier` |
| **상품 · 렌트구분** | 수수료 셈법이 **상품별로 다르다**(수수료표 7 셈법) | `product` + `rentKind` |
| **채널 · 담당** | 누구에게 «지급» 하나. 다이렉트면 지급이 «없다» | `channel` + `agent`/`agentCode` |
| 기간 | 대여료의 기준 | `term` |
| 월 대여료 | 수수료 계산의 «밑값» 이다 (셈법 80건이 대여료×기간) | `rent` |
| **청구월** | **접수와 정산을 잇는 유일한 고리.** 강지수팀장이 손으로 넣던 칸 | `billMonth` |

### 「청구월」 을 접수에 다는 이유

시트에서 이 칸은 **사람이** 넣는다. 인도가 끝난 뒤에야 정해지고, 정해지는
순간 그 줄이 그달 원장에 선다. 접수 화면에 없으면 「이번 달 얼마 청구하나」를
접수에서 못 답하고, 결국 시트를 다시 연다. 그 순간 ERP가 정본이 아니게 된다.

그래서 —
- 목록에서 **맨 오른쪽에 못박아**(`.pin-r`) 옆으로 굴러도 안 사라지게 했다
- 상세에서는 kv 열넷 중 하나로 섞지 않고 **띠 하나를 따로** 세웠다(`.bill`)
- 비면 「0」이 아니라 **「미정」** 이다. 「인도가 끝나야 정해진다」는 까닭까지 적는다

### 「상품 · 렌트구분」 을 한 칸에 접은 이유

둘은 따로 읽히는 법이 없다. 늘 「장기렌트 신차」, 「구독 재렌트」로 붙어 나온다.
열을 둘로 가르면 폭만 먹고 읽는 속도는 안 는다.

### 뺀 것

- **보증금** — 접수의 실측 보증금은 거의 전부 0이다. 있는 건만 상세에서 본다.
- **사진** — 운영자는 접수 목록에서 차 «사진» 을 안 본다. 번호와 차명으로 찾는다.
  대신 그 자리를 접수일에 줬다.

## 3. 상세패널 — 어떻게 구현했나

### 상품 상세 — 다섯 묶음

ERP5 `policy` 가 상품 하나에 매다는 원자가 **81 가지**다.

- 81개를 그냥 쏟으면 아무도 안 읽는다
- 골라서 다섯 개만 보이면 나머지 76개는 «어디에도 없는 값» 이 되고, 결국 시트를 연다

그래서 셋을 지킨다 (`admin-shell.policy.js`) —

1. **다섯 묶음으로 순서를 정해 세운다.** 순서는 상담원이 고객에게 말하는 차례다
   — 차량정보(위 카드) → 대여료·납입 → 보험 조건 → 계약 조건 → 기타·운영
2. **묶음에 안 든 원자는 버리지 않고 「그 밖에」 로 접어 둔다.**
   버리면 사람이 시트를 다시 연다
3. **값이 없는 줄은 안 그린다.** 「미확인」을 81줄 그리면 그게 소음이다
   (살림살이 칸 `sheet_synced_at`·`createdAt`·`*_legacy` 는 「그 밖에」에도 안 넣는다)

값의 «꼴» 은 `type` 이 진다 — `MONEY`는 원, `PERCENTAGE`는 %,
`NUMBER`는 자릿점, **`BOOLEAN`은 「예/아니오」가 아니라 「가능/불가」**.
조건을 말하는 칸이라서다.

### 접수 상세

kv 열넷 + **청구월 띠** + 진행 넷 + 어디까지 왔나 + 메모 + 이력.
새로 선 칸: 상품 · 계약형태 · 납입 · 출고지역 · 영업자코드 · 인도희망 · 인도완료.

## 4. 표와 단추의 문법 — 「선」과 「면」

> 대표 2026-09-17
> 「그냥 표는 선과 버튼은 면으로만 이뤄지고…. 딱 이느낌」
> 「아주 심플하게…. 선이 있어야할곳 면으로만 이뤄져야할곳… 버튼은 어떻게??
>  면과 터치감으로」
> 「누르는 단추의 규격은 다 위계 맞춰서 동일해야지 가로 사이즈는 차이가
>  날것이지만 세로 사이즈는 동일해야지」

| | 쓰는 것 | 어디에 |
|---|---|---|
| **선** | 테두리·밑선·왼쪽 막대 | 표 · 판의 경계 · 입력칸 · 상태 딱지(`.st`) |
| **면** | 채움 | **누를 수 있는 것 전부** |

- 표에서 **면을 전부 뺐다** — 얼룩·머리 띠·고른 줄의 색칠까지.
  고른 줄은 «왼쪽 3px 키색 선 + 위아래 키색 선» 으로 말한다. 색칠 없이도 또렷하고,
  옆 줄 글자가 안 죽는다.
- 단추에서 **선(테두리)을 전부 뺐다.** 터치감은 셋으로 낸다 —
  높이는 하나 / hover 에 한 단 진해지고 / **`:active` 에 1px 내려앉는다**.
- **레트로도 같은 문법이다.** 레트로의 볼록한 베벨은 그 자체로 「면 + 터치감」이라
  원래 같은 것이었다. 높이를 되돌리던 규칙(`--h-s` 24 · `.btn.sm` 20)을 전부 뺐다.

### 단추 높이 — 규격이 이미 있었다

셋(38·30·22)으로 나눠 놨던 것은 **규격을 안 보고** 한 것이다.

```
C:\dev\ai-core\design-system\tokens.css        --control-height   «하나»
C:\dev\ai-core\docs\SCREEN_DESIGN_STANDARD.md  §7
  「Interactive targets use a 44px minimum control height for touch usability.
   WCAG's minimum target-size requirement remains the compliance floor.」
```

44는 **손가락** 값이다. 마우스로 하루 여덟 시간 훑는 목록 화면에 44 단추를
박으면 줄(34)보다 단추가 커진다. 그래서 두 값으로 나눈다 — 규격을 어기는 게
아니라 **규격대로** 다:

| | `--h-btn` | 근거 |
|---|---|---|
| 마우스 | **28px** | WCAG 2.2 AA §2.5.8 의 바닥(24×24)을 넘는다 |
| 터치 `@media (pointer:coarse)` | **44px** | AI Core 가 권하는 손가락 값 그대로 |

위계는 **가로 폭과 면의 무게** 가 진다. 세로는 «절대» 안 진다.
실측으로 확인했다 — 트렌디/레트로 × 밝게/어둡게 **네 벌 모두, 네 화면 모두,
화면에 선 단추 전부가 28px**.

AI Core §28 이 요구하는 단추의 여섯 낯도 다 채웠다 —
`default` · `hover` · `focus-visible` · `active` · `disabled` · `busy`.
★포커스 고리는 키색이 «아니다». 키색은 「골랐다」가 이미 쓰고 있어서
`--color-focus`(주황)로 따로 둔다. AI Core 가 focus 를 따로 둔 이유가 이것이다.

## 5. 열한 칸이 화면보다 넓을 때

ERP 목록에서 열 열둘은 흔하다. 폭에 맞춰 글자를 줄이면 「연식」이 「연」이 되고,
그 순간 아무것도 못 읽는다. ⇒ **찌그러뜨리지 않고 옆으로 구르게 둔다.**

다만 그냥 두면 가장 중요한 칸이 제일 먼저 밀려난다. 그래서 —

```
 ┌─────────┬──────────┬ ── 가운데만 구른다 ── ┬──────────┐
 │ 접수일  │  할 일   │  고객 … 월 대여료    │  청구월  │
 │ (왼쪽 고정)         │                      │ (오른쪽 고정)
```

굴러도 「**언제** 들어온 것을, **무엇을** 해야 하고, **몇 월에** 청구하나」는
항상 보인다. 상품 목록은 열 칸이 그대로 들어가 구르지 않는다(실측 889 / 889).

## 아직 안 한 것

- `policy` 원자 81 중 묶음에 자리를 안 준 것들 — 「그 밖에」에 접혀 있다.
  실제 화면에서 자주 열리는 것이 생기면 묶음으로 올린다.
- 접수의 `region`·`payKind` 로 거르는 세부필터 갈래는 아직 없다.
- 「칸 고르기」(사용자가 열을 켜고 끄기)는 안 만들었다. 먼저 «기본 열» 을
  맞게 고르는 것이 순서다.
