# freepasserp.com v1 — Atom-first ADMIN UI Contract

작성일: 2026-09-13
목적: UI/UX가 데이터를 새로 만들어내지 않고, ERP4에서 검증된 ‘원자’ 철학을 참고해 freepasserp.com v1의 Canonical 원자 중 업무에 필요한 값만 투영하도록 고정한다.

## 1. 핵심 원칙

1. 화면은 원자를 다시 해석하지 않는다. 이미 확정된 Canonical/Resolved 값을 포맷만 한다.
2. ‘필드가 있으니 다 보여준다’가 아니라, 현재 업무 판단에 필요한 최소 원자만 기본 노출한다.
3. 목록은 찾기, 상세는 확인, 업무패널은 실행에 집중한다.
4. 미확인값을 0/불가/무제한으로 바꾸지 않는다. 모르면 ‘미확인’ 또는 생략한다.
5. 배지·요약문은 원자/Policy/Offer에서 근거가 있을 때만 계산한다. 감성적·추정형 배지는 만들지 않는다.
6. 내부 메타·원문·검수정보는 ADMIN의 진단/상세에서만 필요 시 펼친다. 목록 카드에 흘리지 않는다.
7. 기존 ERP4의 DB/API/Firebase/시트를 연결하는 것이 아니라, 원자 필드의 의미와 UI 투영 원칙만 참고한다.

## 2. ERP4에서 확인한 원자 분류 참고

ERP4 atom-fields는 원자를 공통/변동/정책/메타로 분리하고, 새로 들어온 미등록 키는 ‘비공통’으로 드러내는 구조였다.

공통 원자 예시:
- car_number
- origin / maker / model / sub_model / trim_name
- options
- ext_color / int_color
- year
- fuel_type / engine_cc / seats / drive_type / battery_capacity
- vehicle_class / product_type
- photo_link / first_registration_date

변동 원자 예시:
- status / status_kind / status_reason / vehicle_status
- mileage
- price

정책:
- policy_code → 정책 정의 조인

메타 예시:
- provider_company_code / partner_code
- source / source_schema / sheet_source_tab / sheet_source_row
- product_code / listable / 검수상태 / 내부 key

v1은 위 필드명을 그대로 복제하는 것이 아니라, 같은 의미를 Canonical Product / Offer / Policy / Registration / Source Quality 구조에 배치한다.

## 3. 목록 패널 — ‘찾기’에 필요한 원자만

목록 카드 기본 목표: 2줄~3줄 안에서 ‘무슨 차 / 지금 선택한 계약조건 / 판매 가능 여부’를 판단.

### 기본 노출
- 차량 사진 썸네일 1개 (있을 때)
- 모델명
- 확인된 경우에만 세부모델 / 세부트림
- 검색조건과 일치한 Offer의 기간 + 월대여료
- 상태(판매가능/계약중/출고불가 등 확정 상태)

### 조건부 노출
- 실제 주행거리: 중고/실차 상품이고 영업 판단에 중요할 때
- 보증금: 현재 검색조건에 포함됐거나 0원/분납 등 구매 판단에 직접 영향이 있을 때
- 핵심 Policy 1~2개: 예) 21세 가능, 후불, 카드 가능. 실제 유효 Policy만

### 기본 목록에서 빼는 값
- 원산지
- 배기량/인승/구동/배터리 등 세부 제원
- 공급사 코드/원천 시트 행/내부 키
- 원문 전체
- 보험 상세
- 옵션 전체
- 색상 상세
- 계약/정산 내부 메타

이 값들은 검색필터 또는 상세에서 필요할 때만 보여준다.

## 4. 상세 패널 — ‘확인’에 필요한 원자

### A. 요약 탭
1. 사진
2. 모델명 + 세부모델 + 세부트림(확인된 깊이까지만)
3. 선택 Offer
   - 기간
   - 월대여료
   - 보증금
   - 약정주행거리
4. 실차 핵심
   - 연식
   - 실제 주행거리(해당 상품일 때)
   - 차량번호(ADMIN 내부이고 실제 차량이 확정됐을 때)
5. 핵심 Policy 칩
   - 연령
   - 결제시점
   - 카드결제
   - 분납 등 현재 Offer에 유효한 것만
6. `접수하기`

### B. 상세정보 탭
섹션을 데이터 경계 그대로 나눈다.

- 모델정보: 원산지 / 제조사 / 모델 / 세부모델 / 세부트림
- 제원: 연식 / 연료 / 배기량 / 인승 / 구동 / 배터리 / 차급 등 실제 값이 있는 항목만
- 실차/등록: 차량번호 / VIN / 최초등록일 / 실제 주행거리 / 외장 / 내장 / 실제 옵션
- 계약조건: 모든 Offer (기간 / 대여료 / 보증금 / 선납금 / 약정주행거리 등)
- 정책: 적용 가능한 Policy를 의미별로 정리
- 출처/검수: 공급사, 마지막 확인시각, 매칭깊이, 미확인 항목, 원문보기 (접기)

빈 섹션을 억지로 크게 만들지 않는다.

## 5. 업무패널 — ‘실행’에 필요한 원자

### 신규접수
기본 필수값은 업무에 필요한 최소값으로 유지한다.
- 선택 차량/상품 (자동)
- 선택 Offer (자동)
- 영업채널/담당자
- 고객명

연락처 등 추가 필드는 실제 운영 필수 여부가 확정될 때 반영한다. 상품 설명용 원자를 접수폼에서 다시 입력하지 않는다.

### 접수목록
- 고객명
- 차량명
- 접수번호
- 계약서/서류/인도 체크
- 취소 상태
- 필요 시 담당자/채널

가격·원천·제원 전체를 목록에 반복하지 않는다.

### 접수상세
- 접수 당시 Snapshot의 차량/Offer 핵심값
- 계약서 / 필수서류 / 인도 / 취소
- 변경이력

현재 상품 상세와 접수 Snapshot을 혼동하지 않도록 ‘접수 당시 조건’을 명시한다.

## 6. 검색/필터와 UI의 관계

필터는 원자 필드 전체를 다 화면에 나열하는 것이 아니다.

- Quick Filter: 자주 묻는 정책/조건
- Detailed Filter: 모델/제원/Offer/Policy 축
- Filter finder: ‘카드’, ‘후불’, ‘분납’처럼 필터 항목 자체를 찾는 기능

필터 결과 카드에는 ‘검색에 실제로 일치한 Offer’를 표시한다. 18개월 필터인데 60개월 최저가를 보여주지 않는다.

## 8. 시안 검수 질문

새 UI 이미지를 승인하기 전 아래를 본다.

1. 목록 카드가 원자 설명서처럼 복잡해지지 않았나?
2. 검색 결과에 일치 Offer가 바로 보이나?
3. 상세 요약만 보고 접수 여부를 판단할 수 있나?
4. 세부 제원은 상세 탭에서만 필요한 만큼 보이나?
5. Policy 배지가 실제 원자에서 계산된 것인가?
6. 공급사/원문/검수 메타가 메인 UI를 오염시키지 않나?
7. 부분매칭 상품을 완전한 트림처럼 표시하지 않나?
8. 접수폼에서 상품 원자를 다시 입력하게 만들지 않았나?
9. 관리자 업무의 핵심인 검색→상세→접수가 한 화면에서 끊기지 않나?
10. 모바일에서도 같은 정보 우선순위를 유지할 수 있나?

## 9. 디자인 문장

> freepasserp.com v1 ADMIN은 ‘모든 데이터를 보여주는 ERP’가 아니라, Canonical 원자 중 현재 판단에 필요한 값만 단계적으로 투영하는 검색·접수 도구다. 목록은 찾기, 상세는 확인, 업무패널은 실행에 집중한다. 데이터는 많아도 화면은 단순해야 한다.
