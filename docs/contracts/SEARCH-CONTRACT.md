# Search Contract v1

상태: `CODED / TESTED` (회귀테스트 `src/domain/search/__tests__/*.test.ts`)
근거: `AGENTS.md` §5 §6 · `docs/WORK-INBOX.md` §5 · `docs/architecture/v1-core.md` Search

검색은 이 프로젝트의 완료 기준이다. 상품을 많이 저장하는 것이 아니라, **실제로 함께 적용 가능한 조건**을 정확히 찾아 그 조건 그대로 상세와 접수까지 이어가는 것이 목표다.

아래 규칙에는 번호가 있다. 구현과 테스트는 이 번호를 인용한다.
**테스트를 고쳐서 통과시키지 않는다.** 규칙을 바꾸려면 사용자 확인 → 이 문서 수정 → 테스트 수정 순서로 간다.

---

## 축 결합

**S-01 같은 축은 OR, 다른 축은 AND**
한 축에 값을 여러 개 주면 그중 하나만 맞으면 된다. 서로 다른 축은 모두 맞아야 한다.

**S-13 Offer 없는 상품은 결과에 넣지 않는다**
접수로 이어질 계약조건이 하나도 없는 상품은 「찾았다」고 하지 않는다.

---

## Offer

**S-02 같은 Offer 하나가 다 만족해야 한다**
기간 · 월대여료 · 보증금 · 약정주행거리 · Offer 범위 정책은 **하나의 Offer**가 동시에 만족해야 한다.
A Offer의 대여료와 B Offer의 보증금을 합쳐 실재하지 않는 조건을 만들지 않는다.

**S-03 일치한 Offer는 끝까지 따라간다**
결과는 조건을 만족한 `offerId` 전부를 싣는다. 카드 → 상세 → 접수는 이 id를 그대로 쓰며, 화면이 다시 고르지 않는다.

---

## 차종

**S-04 확정된 깊이까지만 믿는다**
상품의 차종 경로는 `matchLevel`까지만 유효하다. 데이터에 그보다 깊은 id가 남아 있어도 검색은 쓰지 않는다.
(`MODEL` = 원산지·제조사·모델까지 확정 · `SUB_MODEL` = 세부모델까지 · `TRIM` = 세부트림까지)

**S-05 확정값이 다르면 제외한다**
상품이 그 축에 **확정값**을 가지고 있고 요청 집합에 없으면 제외한다.
다른 세부모델로 확정된 상품을 PARTIAL에 섞지 않는다.

**S-06 더 깊은 질문에는 PARTIAL로 답한다**
요청 축이 상품의 확정 깊이보다 깊으면 — 제외하지도, EXACT로 올리지도 않는다.
`PARTIAL`로 표시하고 **어느 축이 미확정인지**(`unconfirmedAxes`) 남긴다. 모르는 하위를 채워서 확정처럼 꾸미지 않는다.

**S-07 UNMATCHED 는 차종 질의에서 빠진다**
차종 축이 하나라도 걸린 검색에서 `UNMATCHED` 상품은 제외한다. 확정된 노드가 없으므로 「그 차일 수도 있다」가 모든 차종에 대해 참이 되어 결과가 오염된다.
차종 축이 없는 검색(가격·정책만)에서는 정상 포함한다. UNMATCHED 는 검수 대상이지 숨길 대상이 아니다.

## 미확인 값

**S-08 미확인 ≠ 0 / 불가 / 무제한**
값이 비어 있는 필드는 **어떤 수치 조건도 만족하지 않는다.**
보증금 공란은 「보증금 0원」 검색에 들어가지 않는다. 약정주행거리 공란은 무제한으로 치지 않는다.
현재 차량 주행거리 공란/0도 「0km 차량」으로 해석하지 않는다.

**S-09 정책 미기재 ≠ 거짓**
정책값이 없으면 `true` 요구에도, `false` 요구에도 걸리지 않는다. 「없다」와 「안 된다」는 다르다.

**S-14 현재 차량 주행거리와 연 약정주행거리는 다른 축이다**
- 현재 차량 주행거리 = Product/Vehicle fact (`specs.mileageKm`)
- 연 약정주행거리 = Offer contract fact (`Offer.annualMileageKm`)

둘 중 하나로 다른 하나를 추정하지 않는다.
자연어 검색에서도 `연 2만km`는 약정주행, `주행 5만km`/ `5만km 이하`는 현재 차량 주행거리로 읽는다.

**S-15 공통 Finder의 차량/상품 사실축**
White Label과 Admin이 함께 쓰는 검색 의미는 Domain Search Contract에서 판정한다.
현재 공통 계약에 포함된 사실축:
- 상품구분
- 심사
- 제조사/모델/세부모델/트림
- 연식
- 연료
- 현재 차량 주행거리
- 기간/월대여료/보증금/연 약정주행거리
- 정책

Admin의 공급사·출고상태 같은 내부 운영축은 확장 가능하지만, 위 공통축의 의미를 별도 엔진에서 다시 정의하지 않는다.

## 정책

**S-10 정책 해석 = 상품정책 + Offer정책**
적용 정책은 상품 정책 위에 Offer 정책을 덮어 만든다(같은 `policyId`면 Offer 가 이긴다).
검색 · 상세 · 접수 Snapshot 은 **같은 함수**(`src/domain/product/resolve-policies.ts`)를 쓴다. 두 군데서 따로 해석하면 화면과 접수가 갈린다.
접수 Snapshot 은 해석 결과가 아니라 **두 겹(상품 정책 · Offer 정책)을 그대로** 보존한다. 나중에 해석 규칙이 바뀌어도 당시 원자를 다시 읽을 수 있어야 하기 때문이다.

**S-11 MULTI_SELECT 는 OR**
요청값 중 하나라도 실제 배열에 있으면 만족한다.

## 정렬

**S-12 EXACT 가 PARTIAL 보다 먼저**
같은 등급 안에서는 **입력 순서를 유지**한다(stable).
가격·인기·최신 등 그 밖의 정렬 기준은 `DECISION REQUIRED` — 정하기 전에는 임의로 넣지 않는다.

---

## DECISION REQUIRED

1. **정렬 기준** — EXACT/PARTIAL 다음의 기본 정렬을 무엇으로 할지(최저 월대여료 · 최근 등록 · 공급사 우선순위).
2. **무제한 주행거리 표현** — 지금 타입에는 「무제한」을 적을 칸이 없다. 공란과 구분되는 명시적 표현이 필요하다(S-08 때문에 공란으로 두면 영영 안 잡힌다).
3. **텍스트 검색** — main 프로토타입의 문자열 포함 검색은 이 계약에 없다. 차종명 텍스트를 어느 축으로 해석할지 미정.
4. **보증금 분납·선납 등 금액 축** — `prepayment` 는 아직 검색 축이 아니다.
